## 2. 模型选型（6 分，重点）

**核心思路：三个模型不是「按难度分档」，而是「按角色分工」——架构、开发、审查三权分离。**

这样做的好处是：写方案的不写代码，写代码的不给自己判卷，审查的没参与过前两步。三个角色的视角不同，交叉验证比一个模型从头干到尾可靠得多。

| 模型 | 角色 | 负责什么 | 为什么是它 |
|---|---|---|---|
| **DeepSeek-V4-Pro** | 架构师 | `schema.sql` 表结构与约束、L1-6 下单事务方案（行锁 vs 原子 UPDATE）、L2-10 并发设计、L2-9 支付幂等设计 | 这几处一旦错了是**静默错误**——不报错，但会超卖或重复支付，测试没写对根本发现不了。需要一次想清楚「锁 → 校验 → 扣减 → 插入」的完整时序和失败回滚点，还要能论证为什么选 A 不选 B。这是全项目推理密度最高的一段 |
| **DeepSeek-V4.1-Flash** | 开发者 | 商品 CRUD、订单/支付的 Controller 与 DTO、Repository 的 SQL、单元测试用例、文档整理 | 这类活模式高度固定：题目的字段、状态码、错误码已经全部给死，模型要做的就是照着实现，不需要做设计决策。用 Pro 做这部分是浪费——它在固定套路上的产出并不会更好，只会更贵更慢 |
| **GLM-5.3** | 审查者 | P08（L0 独立验收）、P13（全量复审）：缺陷、边界、事务正确性 | 审查的价值在于「没参与开发」的视角。**必须开新会话、只给题目和代码**，否则等于让实现者给自己判卷。用与架构/开发不同的模型，还能得到第三方的判断——它对前两个模型的方案没有「我写的所以是对的」的偏见 |

**分工在实践中的两个关键点：**

1. **架构师的方案我会自己复核，不是照抄。** 例如 DeepSeek-V4-Pro 推荐条件原子 UPDATE 而非行锁，我在实测 H2 的锁行为后否掉了它，选了行锁（理由见 `DESIGN.md` §5）。架构师的产出是「候选方案 + 论据」，最终拍板的是我。
2. **审查者会指出架构师和开发者都漏掉的问题。** GLM-5.3 在 P08 指出了 `SUBMISSION.md` 空模板、在 P13 指出了字符串字段数字强转的边界——这两处前者是开发者视角的盲区（只关心代码），后者是架构师视角的盲区（只关心数据正确性，不关心输入口径）。

**这套分工的成本**：每个角色切换都要重新交代上下文（不能把上一个模型的对话直接喂给下一个，那样会让审查者带上实现的偏见），所以三个模型各自维护过独立上下文。但这是审查有效性的前提，不是浪费。

## 3. 挑 4 个场景写下来（5 分）

### 场景 1（成功案例）：商品模块一次开发并通过测试

- **对应需求**：L0-2 ~ L0-5，`backend/README.md` §4
- **用哪个模型**：**DeepSeek-V4.1-Flash**（开发者角色）——商品模块是固定套路，不需要做设计决策
- **我怎么问的**：没有一次性把整个项目丢给它。先只给 `schema.sql` 和 `backend/README.md` 里 L0 那一节，要求「实现商品的发布/列表/详情/上下架，所有错误按 §3 码表返回，参数校验用 `@Valid`，列表要支持三条件叠加和分页」。**刻意没给订单和支付的内容**——当时还没写到那，给了只会让上下文变长、让它分心去想「后面订单要用到啥」。
- **AI 给了什么**：Controller / Service / Repository 三层 + DTO，结构合理。但第一版列表接口的 `pageSize` 越界是**夹断**（`Math.min(50, pageSize)`）而不是报 400。
- **我的判断**：`P01-需求分析.md` §2.2 里我已经记了这条——前端 mock 是夹断，但后端题目 §3 码表明确「超范围 → 40001」。**这条我否掉了 AI 的实现**，改成越界直接抛 `BusinessException(BAD_REQUEST)`，并补了 `ProductListTest.pageSizeOverMax` / `pageSizeZero` 两个用例固定住。
- **验证命令与结果**：`./mvnw test -Dtest=ProductListTest,ProductCreateTest,ProductDetailAndStatusTest`，36 + 30 + 21 = 87 例全绿。之后 `mvn test` 全量也绿。
- **对应 Commit**：`bf0dbfc feat:实现商品发布接口`、`a134588 feat:实现商品列表和商品详情与上下架接口，并修复已知bug`

### 场景 2（失败案例：AI 实现未满足接口验收）：支付金额取自请求体

- **对应需求**：L2-9，`backend/README.md` §6
- **用哪个模型**：**DeepSeek-V4.1-Flash**（开发者角色）——支付接口的骨架是常规编码，但幂等设计的正确性由架构师（V4-Pro）在 P11 阶段定方案，这里 Flash 只是实现
- **我怎么问的**：给了 `orders` 表结构和 L2-9 原文，要求「实现模拟支付，幂等，重复支付 409，返回 `paymentId/orderNo/amount/status/paidAt`」。
- **AI 给了什么**：支付接口能跑，但 `amount` 是从**请求体**里读的（`request.amount`），并且 `payments` 表没有对 `order_no` 加唯一约束，只靠「先查再插」判重复。
- **为什么这算「未满足验收」**：题目 L1-6 已经明确「金额由服务端按数据库价格计算，不接受客户端传值」，虽然那句话是针对下单说的，但支付结算的语义是一样的——让客户端决定支付金额等于让客户端自己定价。而且「先查再插」在并发下两个请求都能通过检查。
- **我的判断与修改**：两处都否掉。① `amount` 改为 `order.totalAmount()`（锁内读到的订单金额），请求体里的 `amount` 字段直接不在 DTO 里定义——Jackson 忽略未知字段，客户端传了也不生效；② `payments.order_no` 加 `UNIQUE` 约束，形成「应用层锁 + DB 唯一约束」双保险。
- **验证**：`PaymentTest.clientAmountIgnored`（传 `amount:1`，断言实际 5970）、`PaymentTest.duplicatePayment`、`ConcurrentPaymentTest`（10 并发同单支付，5 轮，恰好 1 个 200）+ `SchemaConstraintTest.duplicatePaymentForSameOrderRejected`（直接测 DB 唯一约束）。
- **对应 Commit**：`21b2624 feat:实现 L2-9 模拟支付`

### 场景 3（自己修改 AI 方案的案例）：事务方案从条件 UPDATE 改成悲观行锁

- **对应需求**：L1-6 / L2-10
- **用哪个模型**：**DeepSeek-V4-Pro**（架构师角色）——这是全项目推理密度最高的一段，需要它论证方案而非照抄实现
- **我怎么问的**：让它比较两个方案在 7 个维度上的差异（状态与价格一致性、事务原子性、并发超卖、错误区分、失败回滚、H2 兼容性、实现复杂度），并要求**用两个并发事务的时序证明**它推荐的方案，最后说明 `@Transactional` 在什么情况下会失效。
- **AI 给了什么**：推荐**条件原子 UPDATE**（`UPDATE ... WHERE status='on' AND stock>=?`），核心论据是「不依赖 H2 的 `FOR UPDATE` 锁语义」「少一条 SELECT」。
- **我改了吗、为什么改**：**改了，最终选了行锁**，和它推荐的不同。三个理由写进了 `DESIGN.md` §5：① 题目 L1-6 的错误判定顺序是硬性的（不存在 404 → 下架 40902 → 库存不足 40901），条件 UPDATE 一条 SQL 扣失败时无法区分这三种错误，还得回查一次商品，简洁性优势就没了；② 行锁的判断顺序和题目叙述顺序完全同构，评审读代码不用做「affected==0 到底是哪种错」的翻译；③ AI 的核心论据「H2 锁语义不确定」**可以直接实测**，不需要靠信任——实测下来 H2 2.3 上 `FOR UPDATE` 正常串行化。
- **AI 的部分我采纳了**：它列出的「`@Transactional` 失效清单」（类内自调用绕过代理、异常被 catch 吞掉、受检异常默认不回滚）**全部采纳**——Service 里所有步骤都写在 `create()` 一个 public 方法内，业务失败一律抛 `BusinessException`（`RuntimeException` 子类），不 catch 吞掉。
- **验证**：`OrderRollbackTest`（双读数证明扣减后回滚）+ `ConcurrentOrderTest`（5 轮并发不超卖）。
- **对应 Commit**：`0c3abf6 feat:悲观行锁方案实现 L1-6 下单接口`

#### 4.1 L0 独立验收（P08）

- **我想干什么**：L0 五个接口写完了、自带测试也全绿了，但「我自己写的测试全过」说明不了什么——测试是我按自己的理解写的，理解错了测试也跟着错。所以我想让一个**没参与开发**的视角，只按 `backend/README.md` 的 L0 要求重新审一遍。
- **我怎么问的**（精简）：
  > 你是一名没有参与之前开发的后端评审工程师。请只根据 backend/README.md 的 L0 要求，对当前实现进行只读审查。重点检查：数据库表及约束是否合理；商品发布的字段/类型/状态码；关键词、状态、分类能否组合筛选；分页 total 和 items 是否一致；详情与上下架的异常处理；统一响应是否遗漏 data 字段；是否存在 SQL 拼接、整数转换和分页溢出风险。**不要因为代码看起来合理就认定通过。**

  关键在最后一句——不加这句，它倾向于「读一遍代码然后说看起来没问题」。
- **它做了什么**：没有只读代码，而是真的 `mvn test`（当时 138 个用例）+ **启动服务用 curl 打了约 40 个场景**。几个我自己没测过的点：
  - `page=2147483647&pageSize=50` —— 我代码里 `offset()` 用了 long，它验证确实没溢出成负数。如果我是用 int 算的，这里会 500。
  - 所有错误响应（400/404/405/415）都带 `"data":null`，不是缺字段。
  - `keyword=%` 只命中标题里含 `%` 的商品，不是全表。
- **它指出的问题**：
  1. `SUBMISSION.md` 还是空模板（真问题）；
  2. PATCH 不带请求体时 message 写的是"请求体字段类型不正确"，实际是"缺请求体"——语义偏了，但 code/HTTP 都对，我判断不值得改；

> **我否掉 AI 建议这件事本身**比"它全对"更值得写。第 3 条如果照做，会让一个 3 行的查询变成一个事务，评审看到只会觉得没分清主次。

## 4. 一次被 AI 带偏的经历（必答）

> **用哪个模型**：**DeepSeek-V4.1-Flash**（开发者角色）。这个坑正是分工设计的动机之一——常规编码由 Flash 负责时，它对框架装配的细节不够敏感，于是给出了一个「能跑但不正确」的写法。后面的排查和修复是我自己完成的，没有依赖某个模型来兜底。

- **它给了什么**：让我手工 `new Jackson2ObjectMapperBuilder().build()` 来定制 `LocalDateTime` 的序列化格式（当时想把时间输出成毫秒精度的 ISO 字符串）。
- **当时为什么信了**：代码能跑，时间格式也确实变成了想要的样式，没有报错。
- **你怎么发现的**：后来加严格类型校验时，补 `price: "1990"` 的测试，发现**居然被接受了**。排查发现手工构建的 `ObjectMapper` **不会继承 `spring.jackson.*` 配置**，`allow-coercion-of-scalars=false` 被静默丢掉了——不报错，只是配置不生效。
- **排查过程**（这就是 `DESIGN.md` §6 里写的那个 Bug）：
  1. 先怀疑是 yml 配置项拼错了 → 检查，没错。
  2. 加一个只有 `@RequestBody` 的探针 Controller，绕开所有业务代码 → **仍然接受** `"1990"`，说明问题在反序列化层，不在业务代码。
  3. 打印 `ObjectMapper.getDeserializationConfig()` 里 `ALLOW_COERCION_OF_SCALARS` 的状态 → 发现是 `false`，配置本身是对的，那问题就只能是「这个 ObjectMapper 不是 Spring 用的那个」。
  4. 回头搜「谁新建了 ObjectMapper」→ 找到了手工 `build()` 的那一处。
- **最后怎么修的**：改成注册 `SimpleModule` bean，让 Spring Boot 自动装配到它构建的 `ObjectMapper` 上（见 `config/JacksonConfig.java`）。`WebConfig` 里同样只修改已有转换器的 charset，不新建 mapper。补了 `JsonStrictnessTest.ObjectMapperFeaturesApplied` 直接断言 feature 状态，以及 `OrderCreateTest`/`ProductCreateTest` 从 HTTP 层验证 `"2"`、`2.5`、`2.0`、`true` 全部 400。
- **之后你改了做法吗**：改了。凡是"框架自动装配的东西"，先问**这个 bean 是怎么来的**，而不是看到一个能用的写法就套上去。这条也记进了 `docs/决策与遗留问题.md`，防止再犯。

> 这次被带偏的教训直接决定了 P09 的做法：AI 说"H2 的行锁语义不确定"，我没直接信，而是**写了并发测试实测**。能用实验验证的，就不靠信任。

## 5. 成本（4 分）

**实际消耗：三模型合计 37.70 / 40 元。** 大头是审查者 GLM-5.3（28.76 元），两个 DeepSeek 合计 8.94 元。这个分布本身就是这套分工的成本画像：审查最贵，但它是三权分离里最不可替代的一环——把它砍掉，前两个角色就回到了「自己写、自己判卷」。

| 问题 | 我的回答 |
|---|---|
| 有没有"一次把整个项目/整个文件塞进去"？为什么？ | 没有主动这样做过。每次只给当前阶段相关的文件和题目对应章节——例如写商品模块时只给 `schema.sql` 的 products 部分和 README §4，不给订单/支付的内容。原因有两个：① 上下文越长，模型越容易「顺便」去改不在本次任务范围内的代码，反而要花时间来回退；② 长上下文每次调用都更贵，而 40 元额度要撑完整个 L0+L1+L2。**唯一例外**是 P13 独立审查——审查必须看全貌，这是必要的成本，不是浪费 |
