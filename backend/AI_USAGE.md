### 场景 4：**我用 AI 做验证的一次**（必答，5 分）

> 这条是真实做过的，下面都是可复现的，不是事后编的。

#### 4.1 L0 独立验收（P08）

- **我想干什么**：L0 五个接口写完了、自带测试也全绿了，但"我自己写的测试全过"说明不了什么——测试是我按自己的理解写的，理解错了测试也跟着错。所以我想让一个**没参与开发**的视角，只按 `backend/README.md` 的 L0 要求重新审一遍。
- **我怎么问的**（精简）：
  > 你是一名没有参与之前开发的后端评审工程师。请只根据 backend/README.md 的 L0 要求，对当前实现进行只读审查。重点检查：数据库表及约束是否合理；商品发布的字段/类型/状态码；关键词、状态、分类能否组合筛选；分页 total 和 items 是否一致；详情与上下架的异常处理；统一响应是否遗漏 data 字段；是否存在 SQL 拼接、整数转换和分页溢出风险。**不要因为代码看起来合理就认定通过。**
- **它做了什么**：没有只读代码，而是真的 `mvn test`（138 个用例）+ **启动服务用 curl 打了约 40 个场景**。几个我自己没测过的点：
  - `page=2147483647&pageSize=50` —— 我代码里 `offset()` 用了 long，它验证确实没溢出成负数。如果我是用 int 算的，这里会 500。
  - 所有错误响应（400/404/405/415）都带 `"data":null`，不是缺字段。
  - `keyword=%` 只命中标题里含 `%` 的商品，不是全表。
- **它指出的问题**：
  1. `SUBMISSION.md` 还是空模板（真问题，我确实忘了）；
  2. PATCH 不带请求体时 message 写的是"请求体字段类型不正确"，实际是"缺请求体"——语义偏了，但 code/HTTP 都对，我判断不值得改；
  3. 列表的 COUNT 和 SELECT 是两条独立查询，并发写入时有瞬时不一致窗口。**我否掉了这条**：单机内存库 + 列表弱一致，为它加事务或快照读是过度设计，而且源码注释里已经写明了两条查询共用 WHERE 的意图。
- **结论**：改了 0 行代码，但补了 `SUBMISSION.md` 的待办，并且知道 3 处已知边界可以主动写进 `DESIGN.md`（比被评审问出来强）。

> **我否掉 AI 建议这件事本身**比"它全对"更值得写。第 3 条如果照做，会让一个 3 行的查询变成一个事务，评审看到只会觉得没分清主次。

#### 4.2 下单事务：让它先出方案，再让它实现（P09）

- **我想干什么**：L1-6 要求"扣库存和插订单在同一事务"。我知道要加事务，但不确定**用行锁还是条件 UPDATE**，也不想凭感觉选。
- **我怎么问的**：让它比较两个方案在 7 个维度上的差异——状态与价格一致性、事务原子性、并发超卖、错误区分、失败回滚、H2 兼容性与锁等待、实现复杂度；并要求**用两个并发事务的时序证明**推荐方案，最后说明 `@Transactional` 在什么情况下会失效。
- **它给了什么**：
  - 推荐**条件原子 UPDATE**（`UPDATE ... WHERE status='on' AND stock>=?`），理由是判定压进一条 SQL、不依赖 H2 的 `FOR UPDATE` 锁语义。
  - 时序证明：T1 扣到 0 后 T2 等到锁释放，重新评估 WHERE 得到 0 行 → 40901。
  - `@Transactional` 失效清单：**类内自调用绕过代理**、异常被 catch 吞掉、受检异常默认不回滚。
- **我改了吗、为什么改**：**我最终选了行锁方案**，和它的推荐不同。原因是：
  1. 题目 L1-6 明确要求"查商品 → 不存在 404 → 下架 40902 → 库存不足 40901"，行锁方案的判断顺序和题目的叙述顺序完全一致，评审读代码时不用脑内翻译"affected==0 到底是哪种错"；
  2. 它的核心论据是"H2 的 FOR UPDATE 锁语义不确定"——这个**可以直接实测**，而实测结果（见下）说明 H2 上锁工作正常；
  3. 条件 UPDATE 要在失败时回查一次才能区分三种错误，反而多一条 SQL。

  不过它提的**失效清单我全部采纳了**：Service 里所有步骤都直接写在 `create()` 一个 public 方法里，不拆带 `@Transactional` 的子方法；业务失败一律抛 `BusinessException`（RuntimeException 子类），不用 catch 吞掉。
- **怎么确认改对了**（这部分是关键，不是"跑通就行"）：
  - **并发实测**：`stock=1` 的商品，10 个 curl 并发下单 → 恰好 1 个 `201`、9 个 `409 + 40901`；事后查库存**恰好 0**。这就是 L2-10 要的形状，顺手拿到了证据。
  - **回滚实测**（这条最费劲）：要证明"库存扣了、订单没写成时库存会回来"，故障必须发生在**扣减之后、插入之前**。做法是把 `OrderNoGenerator` 换成测试替身，固定返回一个已存在的订单号 → `INSERT INTO orders` 撞唯一约束。
  - **怎么证明扣减真的在失败之前**：替身在 `next()` 里（此时扣减已执行、事务未提交）用同一连接读一次库存，读到 **4**；请求结束后从外部再读，**5**。一进一出两个读数，才构成"先扣后回滚"的完整证据。只断言最终是 5 是不够的——那也可能是因为根本没扣。
  - 测试不挂 `@Transactional`：测试级事务会让被测事务加入同一事务，永远看不到真实的提交/回滚边界。
- **结论**：**部分采纳**——方案选型否掉它的推荐，失效清单和测试思路采纳。

## 4. 一次被 AI 带偏的经历（必答）

- **它给了什么**：让我手工 `new Jackson2ObjectMapperBuilder().build()` 来定制 `LocalDateTime` 的序列化格式。
- **当时为什么信了**：代码能跑，时间格式也确实变成了想要的样式，没有报错。
- **你怎么发现的**：后来加严格类型校验时发现 `price: "1990"` 居然被接受了。排查发现手工构建的 `ObjectMapper` **不会继承 `spring.jackson.*` 配置**，`allow-coercion-of-scalars=false` 被静默丢掉了——不报错，只是配置不生效。
- **最后怎么修的**：改成注册 `SimpleModule` bean，让 Spring Boot 自动装配到它构建的 `ObjectMapper` 上（见 `config/JacksonConfig.java`）。并在 `WebConfig` 里同样只修改已有转换器的 charset，不新建 mapper。
- **之后你改了做法吗**：改了。凡是"框架自动装配的东西"，先问**这个 bean 是怎么来的**，而不是看到一个能用的写法就套上去。这条也记进了 `docs/决策与遗留问题.md`，防止再犯。

> 这次被带偏的教训直接决定了 P09 的做法：AI 说"H2 的行锁语义不确定"，我没直接信，而是**写了并发测试实测**。能用实验验证的，就不靠信任。
